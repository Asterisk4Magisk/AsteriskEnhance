# Control protocol v1

The companion owns `@asterisk.enhance.dns`. Control requests require a root peer whose kernel `SO_PEERCRED` PID matches the current `@asteriskd.control` listener. It checks this both before and after reading a complete request. Owning root alone is insufficient for control. The companion supplies a separate, random connection cookie on its private Zygisk Next channel; public clients cannot select that cookie. The separate read-only INFO request accepts root peers without a supervisor or control ownership.

All integers below are little endian; only the diagnostic error field is signed. Frames have an exact 40-byte header:

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | Magic `0x314e4541` (`AEN1`) |
| 4 | 2 | Protocol version, 1 |
| 6 | 2 | Opcode |
| 8 | 4 | Body length, at most 1 MiB |
| 12 | 4 | Nonzero request ID, strictly increasing within a connection |
| 16 | 8 | Supervisor instance ID |
| 24 | 8 | Service cycle ID |
| 32 | 8 | Policy generation |

Clients first send HELLO (1) with a nonzero supervisor instance. PREPARE (2), ACTIVATE (3), CHECK (4), DEACTIVATE (5), RELEASE (6) require all three identities. PREPARE carries policy data; ACTIVATE and CHECK each carry an exact eight-byte absolute CLOCK_MONOTONIC expiry. HELLO, DEACTIVATE and RELEASE are bodyless. Unknown versions/opcodes, oversized/truncated frames and invalid body sizes close the transport. Semantically invalid requests return ERROR (8). Successful state changes return ACK (7); HELLO returns CAPABILITIES (9). Every response echoes the exact request identity.

## Bodies

INFO (10) is bodyless and requires zero supervisor/cycle/generation identities and a nonzero request ID. INFO_REPLY (11) echoes the request ID, keeps those identities zero, and carries at most 512 bytes of ASCII text: `AE_INFO 1` followed by exact newline-terminated `versionCode`, `version`, `buildId`, `netd`, `api`, `modes`, `flags`, and `protocol` fields. `protocol` is the capability revision (7), separate from the frame protocol (1). The version and deterministic per-ABI build identifier are compiled into the library loaded in netd. The companion receives the immutable snapshot over its private channel; it does not read module files to report it.

INFO is a one-shot query. It never enters the control actor, sends HELLO, claims the control client, creates caches, changes a generation, or changes policy lifetime. The broker bounds first-frame concurrency and deadlines and sends this small response without waiting for a slow reader. `asteriskd enhancement-info` exposes this query without starting the supervisor or initializing its configuration, telemetry or network resources. Applications offer an update only when the running versionCode is lower than the version bundled in their own APK. Equal or newer versions still require runtime capability checks; version text and buildId are diagnostic fields and do not trigger an update. Unavailable/older endpoints allow installation. Manager CLI installation success yields a process-local versionCode reboot prompt without inspecting disk state.

CAPABILITIES is 48 bytes: the netd instance as `u64`, followed by ten `u32`: capability revision (7), platform API, supported mode bitmap, mark mask, proxy mark, direct mark, consumer version (2), two reserved zero fields, flags. The frame protocol remains version 1. Mode bits 0/1/2 mean TPROXY/TUN2SOCKS/BPF2SOCKS. Flag bit 0 is reserved and unsupported. Flag bit 1 means native original-network discovery; bit 2 means original DNS route export; bit 3 means release-progress events (see NETWORK_CHANGED). Production clients require revision 7 and both facilities, and reject the reserved flag. Capabilities depend on resolved netd/resolver interfaces and ready hooks/backend/query tracking for every ABI: compatible API 33+ systems advertise bits 0–2, earlier systems advertise bits 0–1. BPF attachment compatibility is evaluated by the supervisor and helper at runtime. Missing interfaces or failed initialization advertise zero modes; there is no architecture or build ID allowlist. Capability negotiation does not bypass the consumer's actual route-readiness checks or BPF attachment compatibility checks.

PREPARE begins with ten `u32`: run mode (1/2/3), list mode (whitelist 1 / blacklist 2 / global 3), consumer version (2), existing entry port, mark mask, proxy mark, direct mark, UID count, forced-bypass UID count, original-network count. A separate `u64` netd instance follows at offset 40. Arrays start at offset 48 in that order. Lists are sorted, unique and contain full Android UIDs; limits are 8192 + 8192 UIDs and 64 real network IDs (1–65535). The exact length is required; trailing data is rejected. Consumer 1 is rejected before allocation; the active consumer version is 2.

A zero original-network count requests native discovery. The actor obtains a bounded sorted inventory from its validated platform backend before allocating caches; an empty or invalid inventory fails preparation. It checks inventory changes on activation and event-triggered checks as well as comparing DNS settings. A changed network set or DNS configuration withdraws the old generation and returns CACHE_ERROR; clients must prepare a new generation. Nonempty network lists explicitly select original networks. Boot startup never depends on an app process or persisted network IDs.

The current profile contract uses mask `0x61000000`, proxy mark `0x21000000`, and direct mark `0x41000000`. The module supplies the final proxy routing mark before socket routing. TPROXY/TUN2SOCKS OUTPUT only exits the ordinary classifier for marked DNS; BPF2SOCKS consumes the mark directly. Enhanced IPv4 TPROXY requires preferred source `127.0.0.1` on its existing local default route. Core GID and forced bypass UIDs take precedence. Original network fwmark fields remain intact. The logical cache ID never replaces the real network ID in the socket mark.

ACK/ERROR bodies begin with 24 bytes: netd instance `u64`, then result code, phase, retained cache count and reserved zero (`u32` each). Results: OK 0, INVALID 1, UNSUPPORTED 2, STALE 3, BUSY 4, CACHE_ERROR 5, DRAINING 6, EXHAUSTED 7, IO_ERROR 8. Phases: IDLE 0, PREPARED 1, ACTIVE 2, DRAINING 3.

A PREPARE CACHE_ERROR always appends 16 bytes: stage (`u32`), reason (`u32`), underlying error (`i32`, negative errno where available), and network ID (`u32`, zero when unavailable). Stages are unknown 0, discovery 1, configuration read 2, cache reservation 3, cache configuration 4, snapshot check 5, routes 6, release 7. Reasons are unknown 0, not ready 1, original configuration changed 2, private DNS 3, NAT64 4, invalid configuration 5, backend failure 6, capacity 7. The original failure is preserved across rollback. No addresses, domains or UIDs are included. Applications and the bundled module require matching revision 7; other revisions are rejected, not negotiated.

The supervisor retries initial preparation at most three times within the eight-second startup budget, including activation. Only not-ready discovery/read of real networks and a changed original snapshot are transient. Retry requires IDLE and zero retained caches. Each retry advances the generation on the authenticated connection, waits through the reactor for a resolver event (with only the original absolute operation timeout), and remains interruptible by stop/child failure. Permission, unsupported configuration, unknown errors and incomplete cleanup fail immediately. Hot transitions retry transient preparation only after a network event within their original eight-second budget, preserving the waiting guard.

The successful consumer-2 PREPARE ACK appends a `u32` route count and 0–64 exact 32-byte records: original network ID, original DNS mark, address family (4/6), IPv6 scope ID (`u32` each), then 16 address bytes in network byte order. IPv4 uses the first four bytes with zero padding and zero scope. The mark comes from the verified original NetworkController function for UID 0 on that network; addresses come from the original configuration copied into the reserved cache. Missing, changed, malformed or oversized route inventories fail preparation and roll back owned caches. The maximum response is 2116 bytes including its header.

Before ACTIVATE, the daemon verifies module capabilities, consumer readiness, installed rules, and cache preparation. Startup and resume do not send synthetic DNS queries or inject reserved answers into core configurations.

## Lifetime and deadlines

ACTIVATE and CHECK carry the client's absolute CLOCK_MONOTONIC expiry (`enqueue time + 2000 ms`). The private channel also carries the broker's framing deadline; the session uses the earlier expiry. The writer checks the deadline after potentially blocking resolver-configuration calls. Failed private exchanges close the channel so late replies cannot satisfy another request. Request budgets exclude system suspend.

ACTIVATE publishes the prepared policy for the lifetime of its control connection. There is no periodic renewal or policy expiration. CHECK validates the active configuration only when a resolver-change event arrives; it cannot activate a prepared generation. A stalled supervisor with a connected socket leaves its last policy active. PREPARE retains ownership immediately after reservation, including when later configuration or rollback fails.

NETWORK_CHANGED (12) is an unsolicited, bodyless event with request ID 1 and zero supervisor/cycle/generation identities. Resolver configuration, cache-deletion and NAT64-prefix hooks signal an eventfd (configuration of the module's own isolated caches is ignored) without taking the writer lock or making Binder calls. The runtime coalesces these signals and the broker forwards events, including those arriving before a command response. Clients defer CHECK until any current operation completes. With flag bit 3, the same event is also sent once when a RELEASE that answered DRAINING can proceed (the last tracked query ended); automatic release after disconnect uses the same wakeup instead of a timer. Until that release finishes, a new owner's PREPARE answers BUSY with phase DRAINING; the client treats it as transient and retries after this event, bounded by its startup deadline. Own-cache activity does not create recurring checks. Network discovery remains native and does not require a running application process. API27 has no experimental TLS-validation completion callback: on actual DNS requests its local resolver state is checked before decoration; unsupported state blocks selected queries using the unavailable cache ID and signals the same event. This path performs no Binder or network requests and adds no idle timer.

DEACTIVATE withdraws the snapshot and acknowledges withdrawal. RELEASE waits for both snapshot readers and their accepted resolver workers before deleting caches. Failed deletions remain owned for retry. Disconnect withdraws and automatically reaps when quiescent. Private-channel reconnect preserves retained resources but never restores the previous policy. Without an acknowledged withdrawal, closing the connection requests best-effort cleanup; a blocked module has no guaranteed revocation deadline.

Idle broker and netd workers wait for socket/events rather than fixed-interval polling. Timeouts remain for partial requests and retained-cache cleanup. Normal suspend does not invalidate an active generation.

Offline discovery is successful PREPARE with a zero route count (68-byte frame). ACTIVATE publishes a zero-cache UID guard; the daemon reports `waiting-network` while core/rules remain running. Selected queries without a cache use the never-allocated resolver netId `0x7fffffff` and cannot consume the original shared cache. CHECK compares even an empty inventory, and network changes rebuild a fresh generation. The guard survives automatic topology draining and is removed on explicit withdrawal or disconnect.

Energy policy: steady waiting-network has no periodic wakeup or network probe. Cache-miss queries do not request inventory rescans; resolver hooks deliver topology/configuration events. A transient retry waits for such an event and keeps one absolute timeout. Pending hot commands wait on socket readiness instead of a 20 ms progress timer. With flag bit 3, resource draining waits for the release-progress event instead of retrying RELEASE; legacy modules keep a 20 ms retry. When a network-driven rebuild exceeds its timeout only while draining or waiting for a network event, the daemon logs it and keeps waiting without a timer instead of stopping the service.

Validation reads each original configuration once per ACTIVATE/CHECK and consumes it immediately while checking its isolated copy. No configuration snapshot survives the operation. Automatic cleanup retains failed deletions without a periodic retry timer; later network/control events retry them. Waiting for outstanding readers/workers still uses the existing quiescence check before deletion.
